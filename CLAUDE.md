# CLAUDE.md

Guardrails for working in this repo. Full setup/architecture docs live in
[`README.md`](./README.md) - this file is what to check *before* acting,
not a duplicate of it.

**Project**: internal Next.js tool for GCS staff — pick a Program of
Interest, enter a client name and a few program-specific variables,
download a branded one-page A4 PDF investment estimate. See
`investment-estimate-tool-spec.md` for the full product spec this
implements.

## Rule: check both skills before any UI or PDF-template change

Before considering **any** change to `app/`, `components/`, or
`lib/pdf/print-template.ts` done, check it against **both**:

- **`.claude/skills/web-design-guidelines`** (added to this repo, not
  globally installed) - interaction/accessibility rules: focus states,
  semantic HTML, `prefers-reduced-motion`, ARIA, alt text.
- **`gcs-design-system`** - brand tokens: Night Blue `#000957`, Electric
  Blue `#3F8CFF` (accent only), sharp corners (`--radius: 0`), Yrsa
  (headings, weight 400) / Heebo (UI text) / JetBrains Mono (tabular/IDs).

This is a hard requirement, not a nicety: a change that skips this check
is not finished, even if it looks right.

## Things that will bite you if you don't know them

- **`AGENTS.md` is not real project guidance.** It's regenerated by
  `next dev` itself (see
  `node_modules/next/dist/server/lib/generate-agent-files.js`) — a stock
  Next.js 16 dev-server artifact telling agents to read Next's own
  bundled docs, not this repo's conventions. Don't add project rules
  there; they'll look like they "belong" but this file (`CLAUDE.md`) is
  where this repo's real guardrails live.
- **PDF Chromium has two divergent code paths.** `lib/pdf/render-pdf.ts`
  picks `@sparticuz/chromium` (serverless-compatible build) when
  `process.env.VERCEL` or `AWS_LAMBDA_FUNCTION_NAME` is set, otherwise a
  local binary (`LOCAL_CHROMIUM_PATH` env var, or `/opt/pw-browsers/chromium`
  if unset). A change that only passes `npm run build` can still fail on
  Vercel — always verify a real `/api/generate-pdf` call after touching
  `render-pdf.ts`, not just a clean build.
- **The Chromium instance is a warm, module-level singleton — don't
  reintroduce per-request `launch()`.** `getBrowser()` in
  `lib/pdf/render-pdf.ts` caches the launched browser across warm
  invocations and checks `browser.connected` before reuse, relaunching
  only if it's died. Only the per-request `Page` gets closed after each
  render; the `Browser` itself must never be closed by a request handler
  — that would silently undo the whole point of the cache. This is the
  spec's own stated preference (§2: "a persistent/warm headless-browser
  instance... rather than spinning one up per request") — the app didn't
  actually implement it until this was fixed.
- **`next.config.ts`'s `outputFileTracingIncludes` is load-bearing, not
  cosmetic.** `@sparticuz/chromium` finds its bundled Chromium binary via
  `path.join(__dirname, ...)` at runtime, which Next's static file tracer
  can't see — without that config entry, a Vercel deploy builds fine but
  fails at runtime with "input directory .../bin does not exist". Don't
  remove it when touching `next.config.ts`.
- **`lib/programs/registry.ts` is the entire extension point.** Adding or
  changing a program should never require touching `app/`, `components/`,
  or `lib/pdf/*` — if it does, something's wrong with the approach, not
  the exception. See README's "Adding a new program" for the checklist.
- **Fee constants are hardcoded per-program with no schema or snapshot
  test to catch a transcription error** (e.g. `REAL_ESTATE_PURCHASE_MIN`
  in `malta-mprp.calculator.ts`). There's no test suite in this repo at
  all — double-check numbers by hand against the source program rules
  before merging a calculator change; nothing else will catch a mistake
  before it reaches a client-facing PDF.
- **No auth is intentional.** Per the spec, this is an internal-only
  tool. Don't add a login flow without confirming that's actually wanted.
